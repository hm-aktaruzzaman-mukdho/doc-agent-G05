These textbooks are dense with historical timelines, geographical maps, multi-column layouts, and tabular demographic data, often requiring a bilingual (Bangla and English) approach.

Here are the state-of-the-art (SOTA) methods for each stage of the pipeline to handle this specific domain.

## 1. Ingestion & Enhancement

Scanned SSC textbooks often suffer from bleed-through, skewed pages, and low resolution. If the visual quality is poor, downstream layout parsing will fail.

* **Dewarping & Deskewing:** Use models like **DocEnTr** or traditional OpenCV pipelines to flatten curved pages (common in thick textbook scans) and align text horizontally.
* **Binarization:** Adaptive thresholding (like Sauvola's method) removes background noise, page discoloration, and text bleed-through from the reverse side of the page.
* **Super Resolution:** For low-DPI historical maps or diagrams, applying models like **Real-ESRGAN** prior to OCR ensures small text inside figures is readable.

## 2. Layout Analysis & OCR

Humanities books do not read linearly. You must detect reading order across sidebars, image captions, and tables.

### Layout Parsing

* **Surya / Marker:** Vik Paruchuri's **Surya** is currently SOTA for line-level layout analysis, reading order detection, and table boundaries. **Marker** wraps this into a pipeline that converts PDFs directly to Markdown, preserving the document's structure.
* **LayoutLMv3:** A multimodal transformer that combines text, layout, and image features to classify document blocks (Title, Text, Table, Figure).

### Bilingual OCR (Bangla/English)

* **Google Cloud Vision API:** Still the gold standard for Bangla OCR, handling complex ligatures (যুক্তবর্ণ) exceptionally well.
* **PaddleOCR (v4):** The best open-source alternative for multilingual OCR, highly customizable for mixed Bangla-English textbook pages.
* **VLM Parsing:** For pages with extreme complexity (e.g., a map of the 1971 sectors with overlapping text), passing the cropped layout block directly to a Vision-Language Model (like Gemini 1.5 Pro or Qwen-VL-Max) to generate a Markdown description often outperforms traditional OCR.

## 3. Chunking Strategies for GK

General Knowledge requires high factual precision. Traditional fixed-size token chunking will split critical dates and events, leading to retrieval failures.

| Strategy | How It Works | Why it fits Humanities & GK |
| --- | --- | --- |
| **Structural Chunking** | Splitting text based on Markdown headers (`## Chapter`, `### Sub-topic`) using tools like LangChain's `MarkdownHeaderTextSplitter`. | Keeps context intact. An entire section on "The Pal Dynasty" stays together, preventing orphan facts. |
| **Propositional Indexing** | Using a lightweight LLM to break complex paragraphs into atomic, self-contained facts (e.g., *"The Battle of Buxar occurred in 1764."*). | SOTA for GK. Ensures dense retrieval vectors are highly concentrated on specific facts rather than diluted by paragraph filler. |
| **Table Serialization** | Converting tables into HTML or Markdown, or generating QA pairs for each row. | Allows the retriever to understand relationships (e.g., matching a river to its length in a geography table). |

## 4. Indexing & Retrieval Design Choices

### Hybrid Search (Dense + Lexical)

Relying solely on vector embeddings is a mistake for GK. Dense vectors (like **BGE-M3** or **mE5**) are great for semantic matching ("ancient wars in Bengal"), but they struggle with exact entity searches. You must use **Hybrid Search**: combining Vector Search with **BM25** (lexical search) to catch exact dates, specific names, and locations.

### Parent-Child (Multi-Vector) Retrieval

Index small, highly specific chunks (or propositions) in the vector database to ensure accurate search hits. However, when a chunk is retrieved, pass its larger surrounding "parent" section to the LLM. This guarantees the LLM has the full historical or geographical context needed to formulate a comprehensive answer.

### Vision-Language RAG (The ColPali Approach)

Instead of fighting the friction of OCR, layout parsing, and table extraction, SOTA architectures are moving toward **Visual RAG**:

1. Treat every textbook page as an image.
2. Use a vision-language encoder like **ColPali** (based on PaliGemma) to generate rich embeddings of the *raw page image*.
3. Store these image embeddings in a vector database (like Vespa or Qdrant).
4. When a user asks a question, retrieve the most relevant page images and pass them directly to a Multimodal LLM to generate the answer.

This approach completely sidesteps OCR errors and perfectly preserves the spatial layout of maps, historical timelines, and demographic tables.

## Executive Summary

| Feature | The Pros (Why it works) | The Cons (Where it breaks) |
| --- | --- | --- |
| **Deterministic Deskew** | Fast, explainable, and CPU-friendly. | Only fixes 2D rotation; fails on 3D page curls. |
| **NLM Denoising** | Preserves text edges brilliantly while removing background grain. | Computationally heavy; extremely slow on high-res scans. |
| **Adaptive Binarization** | The ultimate fix for uneven lighting and spine shadows. | Hyperparameter brittle; can erode delicate Bangla ligatures. |
| **Temp Images (Disk I/O)** | Excellent for debugging and checkpointing long jobs. | Massive I/O bottleneck; drastically slows down ingestion. |

## 1. Deterministic Deskew (minAreaRect / Hough Lines)

This typically involves finding the contours of text blocks, calculating their angle, and applying an affine rotation matrix (`cv2.warpAffine`) to straighten the page.

* **Pros:**
* **Highly Efficient:** It runs strictly on the CPU and requires very little memory.
* **Explainable:** You can visualize the exact lines or bounding boxes the algorithm used to calculate the angle. If it fails, you know why.


* **Cons:**
* **No 3D Dewarping:** A deterministic 2D rotation matrix cannot fix the curved distortion that happens near the spine of a thick textbook. It will straighten the center but leave the edges warped.
* **Vulnerable to Layouts:** If a page contains a lot of vertical tables, diagonal diagrams, or marginalia, the algorithm might align to the wrong dominant angle.



## 2. Non-Local Means (NLM) Denoising

Algorithms like `cv2.fastNlMeansDenoising()` work by taking a small patch of pixels and searching the image for similar patches, averaging them out to remove noise while keeping sharp edges.

* **Pros:**
* **Edge Preservation:** Unlike standard Gaussian blurs that make text fuzzy (ruining OCR), NLM removes background grain and scanner artifacts while keeping the sharp edges of text intact.


* **Cons:**
* **Severe Speed Bottleneck:** NLM is incredibly computationally expensive. Running it on a standard 300 DPI textbook scan (typically 8+ megapixels) can take several seconds per page on a CPU. Multiplied by a 500-page textbook, this single step creates a massive ingestion bottleneck.



## 3. Adaptive Binarization

Instead of using one global threshold for the whole image, `cv2.adaptiveThreshold()` calculates the threshold for small pixel neighborhoods (e.g., an 11x11 grid).

* **Pros:**
* **Conquers Uneven Illumination:** SSC textbooks often have a dark gradient near the spine and bright glares on the edges. Global thresholding turns the shadow into a giant black block. Adaptive binarization successfully extracts text regardless of local lighting.


* **Cons:**
* **Hyperparameter Brittleness:** The `blockSize` and `C` (constant to subtract) parameters are hardcoded. A block size that works perfectly for a 300 DPI scan will completely obliterate the text on a 150 DPI scan.
* **Ligature Damage:** If tuned too aggressively, it will "hollow out" thick text or erase the critical tiny dots (বিন্দু) in Bangla characters (like ড়, ঢ়, য়), causing severe OCR hallucination later.



## 4. Temporary Images (Writing to Disk)

Saving the output of each step (e.g., `page1_deskewed.png`, `page1_denoised.png`) to a temporary folder before passing it to the OCR engine.

* **Pros:**
* **Stateful Debugging:** If the pipeline crashes on page 402, you can open the temp folder and immediately see which processing step destroyed the image.
* **Memory Safety:** It prevents RAM leaks when processing massive PDFs, as Python's garbage collector can struggle with thousands of large NumPy arrays.


* **Cons:**
* **I/O Bound Sluggishness:** Writing an uncompressed image to an SSD takes significantly longer than passing a pointer to a NumPy array in memory. For thousands of pages, Disk I/O becomes the primary limiting factor of your pipeline's speed.
* **Storage Overhead:** Uncompressed intermediate images can quickly consume gigabytes of temporary disk space.

While English OCR is highly resilient to poor scans, Bengali OCR is notoriously brittle. NCTB Humanities books (such as *History of Bangladesh and World Civilization* or *Geography and Environment*) compound this issue because they are heavily text-dense, printed on thin paper, and often poorly scanned.

Here are the specific reasons why preprocessing and enhancement are strictly necessary, and the key points you must address in your pipeline:

## 1. Preserving Complex Bangla Orthography (Ligatures & Modifiers)

Bangla has 11 vowels, 39 consonants, and over 170 compound characters (যুক্তবর্ণ), along with critical modifiers like the *bindu* (the dot under ড়, ঢ়, and য়).

* **The Problem:** If a scan is noisy or low-resolution, standard OCR will mistake a tiny speck of dust for a *bindu*, or conversely, erase a *bindu* due to poor lighting. This turns "পাহাড়" (mountain) into "পাহার" (guard), entirely changing the semantic meaning of a geography or history text.
* **The Fix:** **Non-Local Means Denoising** and **Adaptive Binarization**. You must carefully tune binarization thresholds to remove background noise without eroding the delicate strokes and dots that differentiate Bengali characters.

## 2. Eradicating Text Bleed-Through (Ghosting)

NCTB books are typically printed on thin, low-cost paper. When scanned, the text from the reverse side of the page often bleeds through, creating a faint overlay of reversed text behind the actual content.

* **The Problem:** OCR engines will attempt to read these faint, reversed letters, resulting in massive blocks of hallucinated, nonsensical text mixed into your clean data.
* **The Fix:** **Sauvola or Niblack Local Thresholding**. Global thresholding fails here. You need adaptive algorithms that can distinguish between the dark foreground text and the lighter bleed-through text based on local contrast.

## 3. Correcting Skew and 3D Spine Curvature

Thick textbooks like *Bangladesh and Global Studies* cannot lie perfectly flat on a scanner bed. This creates a severe 3D warp near the book's spine, curving the text lines downward.

* **The Problem:** OCR engines expect text to run in straight, horizontal lines. If the text curves, the bounding box for a single word will accidentally clip the word on the line below it, destroying both words.
* **The Fix:** **Deskewing and Page Dewarping**. You must apply geometric transformations (like OpenCV's `minAreaRect` or deep-learning-based dewarping like DocEnTr) to flatten the page virtually and ensure every line is perfectly horizontal before the OCR reads it.

## 4. Multi-Column & Non-Linear Layouts

Humanities books do not read like a simple novel. A single page might contain a primary text column, a shaded sidebar with a historical timeline, a picture of a monument with a caption, and a demographic table.

* **The Problem:** If you pass the raw image to an OCR engine, it will read straight across the page from left to right. It will mash the sidebar text into the middle of the primary paragraph, completely destroying the reading order and the logical flow of the history lesson.
* **The Fix:** **Layout Analysis (Segmentation)**. You must use layout parsing models (like Surya, LayoutLM, or YOLO) to draw bounding boxes around distinct structural elements first. You then crop these boxes and pass them to the OCR engine individually, preserving the correct hierarchical reading order.

### 1. `ingestion.py` (PDF to Images)

We use `PyMuPDF` (formerly imported as `fitz`) because it is significantly faster than `pdf2image` and allows direct extraction of pages into NumPy arrays without writing temporary files to disk.

```python
import fitz  # PyMuPDF
import numpy as np
import cv2

class PDFIngestor:
    def __init__(self, dpi=300):
        self.dpi = dpi
        # Zoom factor for PyMuPDF based on target DPI (72 is default PDF points)
        self.zoom = self.dpi / 72.0 
        self.mat = fitz.Matrix(self.zoom, self.zoom)

    def extract_page_as_cv2(self, pdf_path, page_number):
        """Yields an OpenCV BGR image directly from memory."""
        doc = fitz.open(pdf_path)
        
        if page_number >= len(doc) or page_number < 0:
            raise ValueError("Page number out of range.")
            
        page = doc.load_page(page_number)
        pix = page.get_pixmap(matrix=self.mat, alpha=False)
        
        # Convert PyMuPDF Pixmap to NumPy array
        img_array = np.frombuffer(pix.samples, dtype=np.uint8).reshape(pix.h, pix.w, pix.n)
        
        # Convert RGB (PyMuPDF) to BGR (OpenCV standard)
        img_bgr = cv2.cvtColor(img_array, cv2.COLOR_RGB2BGR)
        doc.close()
        return img_bgr

```

### 2. `enhancement.py` (OpenCV Preprocessing)

This module addresses the issues of skew, background noise, and uneven lighting common in NCTB textbooks.

```python
import cv2
import numpy as np

class ImageEnhancer:
    def __init__(self):
        pass

    def deskew(self, image):
        """Corrects the rotation of the page using bounding box contours."""
        gray = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
        gray = cv2.bitwise_not(gray)
        thresh = cv2.threshold(gray, 0, 255, cv2.THRESH_BINARY | cv2.THRESH_OTSU)[1]

        # Get coordinates of all text pixels
        coords = np.column_stack(np.where(thresh > 0))
        angle = cv2.minAreaRect(coords)[-1]

        # Fix OpenCV angle output variations
        if angle < -45:
            angle = -(90 + angle)
        else:
            angle = -angle

        # Only deskew if the angle is significant
        if abs(angle) < 0.5:
            return image

        (h, w) = image.shape[:2]
        center = (w // 2, h // 2)
        M = cv2.getRotationMatrix2D(center, angle, 1.0)
        rotated = cv2.warpAffine(image, M, (w, h), flags=cv2.INTER_CUBIC, borderMode=cv2.BORDER_REPLICATE)
        return rotated

    def clean_textbook_page(self, image, binarize=True):
        """Applies NLM Denoising and Adaptive Binarization for Bangla orthography."""
        # 1. Non-Local Means Denoising to preserve text edges while removing grain
        denoised = cv2.fastNlMeansDenoisingColored(image, None, 10, 10, 7, 21)
        gray = cv2.cvtColor(denoised, cv2.COLOR_BGR2GRAY)

        if binarize:
            # 2. Adaptive Binarization to fix spine shadows and bleed-through
            # Block size 31, C=15 is generally safe for 300 DPI textbook scans
            binary = cv2.adaptiveThreshold(
                gray, 255, 
                cv2.ADAPTIVE_THRESH_GAUSSIAN_C, 
                cv2.THRESH_BINARY, 
                31, 15
            )
            return binary
        return gray

```

### 3. `ocr_engines.py` (EasyOCR & Qwen3-VL)

Here we wrap both models. EasyOCR is used for standard text, while Qwen3-VL-4B-Instruct is used as a powerful fallback for complex layouts, charts, and damaged text.

```python
import easyocr
import torch
from PIL import Image
from transformers import AutoProcessor, AutoModelForCausalLM
from qwen_vl_utils import process_vision_info
import cv2

class HybridOCREngine:
    def __init__(self):
        print("Loading EasyOCR (bn, en)...")
        # Load Bangla and English
        self.easy_ocr = easyocr.Reader(['bn', 'en'], gpu=torch.cuda.is_available())
        
        print("Loading Qwen3-VL-4B-Instruct...")
        # Qwen3-VL configuration for complex reasoning and layout extraction
        model_id = "Qwen/Qwen3-VL-4B-Instruct"
        self.vlm_model = AutoModelForCausalLM.from_pretrained(
            model_id, 
            torch_dtype="auto", 
            device_map="auto"
        )
        self.vlm_processor = AutoProcessor.from_pretrained(model_id)

    def extract_with_easyocr(self, cv2_image):
        """Fast, traditional OCR. Best for clean, single-column text."""
        results = self.easy_ocr.readtext(cv2_image, detail=0, paragraph=True)
        return "\n".join(results)

    def extract_with_qwen(self, cv2_image, prompt="Extract all text from this page, preserving Markdown structure, tables, and lists. Keep the language exactly as written."):
        """SOTA VLM Extraction. Best for complex layouts, maps, and damaged text."""
        # Convert OpenCV BGR to PIL RGB for Transformers
        pil_img = Image.fromarray(cv2.cvtColor(cv2_image, cv2.COLOR_BGR2RGB))
        
        messages = [
            {
                "role": "user",
                "content": [
                    {"type": "image", "image": pil_img},
                    {"type": "text", "text": prompt},
                ],
            }
        ]

        # Prepare inputs using Qwen's utility
        text = self.vlm_processor.apply_chat_template(
            messages, tokenize=False, add_generation_prompt=True
        )
        image_inputs, video_inputs = process_vision_info(messages)
        
        inputs = self.vlm_processor(
            text=[text],
            images=image_inputs,
            videos=video_inputs,
            padding=True,
            return_tensors="pt",
        ).to(self.vlm_model.device)

        # Generate output
        generated_ids = self.vlm_model.generate(**inputs, max_new_tokens=2048)
        
        # Trim the prompt from the generated output
        generated_ids_trimmed = [
            out_ids[len(in_ids):] for in_ids, out_ids in zip(inputs.input_ids, generated_ids)
        ]
        
        output_text = self.vlm_processor.batch_decode(
            generated_ids_trimmed, skip_special_tokens=True, clean_up_tokenization_spaces=False
        )
        
        return output_text[0]

```

from ingestion import PDFIngestor
from enhancement import ImageEnhancer
from ocr_engines import HybridOCREngine

def process_textbook_page(pdf_path, page_num):
    # 1. Initialize modules
    ingestor = PDFIngestor(dpi=300)
    enhancer = ImageEnhancer()
    ocr = HybridOCREngine()

    # 2. Ingest
    print(f"Extracting page {page_num}...")
    raw_image = ingestor.extract_page_as_cv2(pdf_path, page_num)

    # 3. Enhance
    print("Deskewing and cleaning image...")
    deskewed = enhancer.deskew(raw_image)
    
    # We create two versions: 
    # - Binary for EasyOCR (needs clean black/white)
    # - High-res color/gray for Qwen3-VL (VLMs prefer natural context)
    binary_img = enhancer.clean_textbook_page(deskewed, binarize=True)
    
    # 4. Extract
    print("\n--- Running EasyOCR (Fast/Lexical) ---")
    easyocr_text = ocr.extract_with_easyocr(binary_img)
    print(easyocr_text[:200] + "...\n")

    print("--- Running Qwen3-VL-4B (Structural/Contextual) ---")
    # Note: We pass the deskewed (but not binarized) image to the VLM. 
    # VLMs perform better when they can see colors, faint lines, and natural shadows.
    vlm_prompt = (
        "You are an expert at digitizing Bengali textbooks. "
        "Extract all text, convert tables to Markdown format, and ignore page numbers."
    )
    qwen_text = ocr.extract_with_qwen(deskewed, prompt=vlm_prompt)
    print(qwen_text)

if __name__ == "__main__":

    # process_textbook_page("history_of_bangladesh_class_9_10.pdf", 45)

### Key Design Choices Addressed

1. **In-Memory Operations:** Notice that `cv2.imwrite()` is never used. The `PyMuPDF` output is converted directly to a NumPy array, processed by OpenCV, and passed straight to PIL/Transformers. This solves the **I/O bottleneck** mentioned earlier.
2. **Dual-Image Strategy:** The pipeline creates a strictly binarized image for EasyOCR (which requires stark contrast to find ligatures) but passes the *unbinarized*, color-deskewed image to Qwen3-VL. Vision-Language models use context (like the color of a sidebar or the gray shading of a table header) to understand layout; binarizing it destroys that semantic data.

            text=[text], images=image_inputs, videos=video_inputs, padding=True, return_tensors="pt"

    except Exception as e:
        return {"page": page_num, "status": "failed", "error": str(e)}

### Why this design avoids Kaggle crashes:

1. **The `spawn` context:** Jupyter defaults to `fork`, which attempts to copy the existing PyTorch state from the main notebook thread into child processes. This immediately crashes Kaggle CUDA drivers. `spawn` creates a fresh, clean Python environment for each GPU.
2. **`CUDA_VISIBLE_DEVICES` Isolation:** Passing `0` to one worker and `1` to the other creates a sandbox. When `device_map="auto"` triggers inside the worker, it only sees *one* GPU, forcing it to load directly onto that specific T4.
3. **Lazy Memory Loading:** By putting the `import torch` and model loading *inside* the `init_worker` function rather than at the top of the file, the main Jupyter thread uses virtually zero RAM, leaving Kaggle's ~30GB System RAM entirely free to handle the two worker processes loading the models.

[AI]:In NCTB Humanities textbooks, non-prose elements (such as callout boxes, sector maps, demographic tables, and historical artifacts) contain **more than 60% of the high-yield General Knowledge (GK) facts**.

If you feed these pages into a standard OCR engine as raw text, two fatal errors happen:

1. **Context Smearing:** A sidebar callout box gets inserted into the middle of an unrelated historical narrative.
2. **Visual Blindness:** Maps, charts, and artifacts lose their spatial relationships, legends, and captions.

Here is the architectural strategy to isolate, extract, and index each of these elements for a SOTA RAG pipeline.

---

## 1. Boxed Works & Callouts (একক কাজ, জেনে রাখা ভালো, সারসংক্ষেপ)

Textbooks use shaded or bordered boxes for two main purposes: **Critical Fact Callouts** (e.g., *"জেনে রাখা ভালো: পলাশীর যুদ্ধের পটভূমি"*) and **Student Activities** (e.g., *"দলগত কাজ: তোমার এলাকার মানচিত্র আঁক"*).

### Extraction & Structuring

* **Segregation:** Do not let box text interrupt the main column flow. Use Layout Analysis (or VLM instructions) to extract the box as an independent structural block.
* **Format:** Convert them into standard Markdown callout syntax:
```markdown
> [!NOTE] জেনে রাখা ভালো
> ১৯৭১ সালের ২৫শে মার্চ রাতে পরিচালিত অভিযানের নাম ছিল 'অপারেশন সার্চলাইট'।

```


* **Filtering Rule:** If building a strict factual QA/GK retriever, classify box types. **Retain** "Important Fact" boxes; **deprioritize or discard** purely pedagogical "Home Task" (`একক কাজ / বাড়ির কাজ`) prompts, as they add noise to dense vector search.

---

## 2. Tables (পরিসংখ্যান, সময়রেখা, ভৌগোলিক উপাত্ত)

Humanities tables (e.g., population censuses, river lengths, chronologies of Mughal rulers) fail in vector search if extracted as raw space-separated text because column headers become detached from cell values.

### Extraction & Serialization

* **Hierarchical Markdown / HTML:** Extract tables into clean Markdown tables with explicit column headers.
* **Row-Level Natural Language Serialization:** For vector databases, convert dense table rows into atomic sentences alongside the table:
* *Raw row:* `| পদ্মা | উৎপত্তিস্থল: হিমালয়ের গঙ্গোত্রী হিমবাহ | দৈর্ঘ্য: ৩৬৬ কিমি |`
* *Serialized chunk:* `"পদ্মা নদী হিমালয়ের গঙ্গোত্রী হিমবাহ থেকে উৎপন্ন হয়েছে এবং এর দৈর্ঘ্য ৩৬৬ কিলোমিটার।"`
* *Why:* Embedding models (like `BGE-M3` or `mE5`) match natural language queries far better against serialized sentences than raw pipe-delimited Markdown tables.



---

## 3. Maps & Spatial Diagrams (মুক্তিযুদ্ধের সেক্টর, ভূ-প্রকৃতি, রাজনৈতিক সীমানা)

Maps cannot be parsed by standard OCR engines because the text is oriented at various angles and text meaning depends on geographic coordinates and map legends.

### VLM-Assisted Map Transcription

Pass cropped map images to a Vision-Language Model (e.g., Qwen-VL) with an explicit extraction schema:

1. **Map Title & Scope:** (e.g., *"বাংলাদেশের ভূ-প্রাকৃতিক অঞ্চলের মানচিত্র"*).
2. **Legend / Key Decoupling:** Extract colors, symbols, and their corresponding meanings.
3. **Entity-Region Mapping:** Transcribe labeled districts, rivers, boundaries, or sectors into an explicit list.

```markdown
<!-- [MAP_START: Sector Map of 1971] -->
**Title:** ১৯৭১ সালের মুক্তিযুদ্ধের সেক্টরসমূহ
**Key Entities Extracted:**
- সেক্টর ১: চট্টগ্রাম, পার্বত্য চট্টগ্রাম ও নোয়াখালী জেলার অংশবিশেষ (কমান্ডার: মেজর জিয়াউর রহমান / মেজর রফিকুল ইসলাম)
- সেক্টর ২: ঢাকা, কুমিল্লা, ফরিদপুর ও নোয়াখালীর অংশবিশেষ (কমান্ডার: মেজর খালেদ মোশাররফ)
<!-- [MAP_END] -->

```

## 4. Historical Figures, Artifacts & Monuments (ভাস্কর্য, মুদ্রা, প্রাচীন নিদর্শন)

Photos of archaeological sites (মহাস্থানগড়, লালবাগ কেল্লা), ancient coins, or historical portraits usually carry essential context in their **captions** rather than the image alone.

### Multi-Modal Metadata Tagging

* **Caption Binding:** Always bind the image bounding box to its nearest caption block (`চিত্র ৩.২: সোমপুর মহাবিহার`).

* *Image reference:* `assets/figures/sompur_bihar_p45.jpg`
* *Description:* *"পাহাড়পুরের সোমপুর মহাবিহারের ধ্বংসাবশেষ। এটি দ্বিতীয় পাল রাজা ধর্মপাল কর্তৃক নির্মিত বৌদ্ধ বিহার, যা নওগাঁ জেলায় অবস্থিত। UNESCO বিশ্ব ঐতিহ্যবাহী স্থান।"*


* **Retrieval Utility:** When the retriever surfaces this chunk, your frontend can render the factual text *and* present the actual image file to the student.

---

### 1. Handling Truncated Texts and Missing Sentences

When an OCR pipeline drops sentences or cuts off paragraphs, it is almost always a failure in the **chunking strategy** or the **layout grouping**, not the OCR engine itself.

**A. Implement Semantic Overlap Chunking**
If your pipeline splits a document purely by character count (e.g., every 500 characters), it will inevitably slice a sentence in half. If the retriever only pulls the first half, the LLM cannot answer the question.

* **The Fix:** Use a chunker that understands sentence boundaries and incorporates an **overlap window**. For example, if Chunk 1 is sentences 1-10, Chunk 2 should be sentences 9-18. This ensures that the transitional context (sentences 9 and 10) is preserved in both vectors.
* **Implementation:** Use LangChain's `RecursiveCharacterTextSplitter` configured to prioritize punctuation (`.`, `।`, `?`) and set a `chunk_overlap` of 10-15%.

**B. Parent-Child Document Retrieval**
If a text block is too small (truncated), it lacks the context needed for a good RAG answer.

* **The Fix:** Index highly granular, atomic facts (the "Child" documents) into your vector database. When a user queries a specific fact, the retriever finds that small child chunk. However, instead of passing just the child chunk to the LLM, your system retrieves the entire original page or paragraph (the "Parent" document) and feeds *that* to the LLM.
* **Why it works:** This guarantees the LLM receives the full, untruncated context surrounding the retrieved fact.

**C. Cross-Column/Cross-Page Merging**
If your OpenCV heuristic parser forces a left-to-right read across two columns, sentences will be physically broken.

* **The Fix:** You must calculate bounding box intersections. If two text blocks share the same horizontal space (Y-axis overlap) but are separated by a large vertical gap (X-axis distance), they are columns. You must instruct the parser to read Column 1 entirely (top to bottom) before moving to Column 2.

---

### 2. Why NFKC Normalization is Required for Bengali

In Unicode, certain characters can be represented in multiple ways. This is disastrous for vector search because if the document uses Representation A, but the user types their search query using Representation B, the lexical search (BM25) will fail to find a match.

**NFKC** stands for **N**ormalization **F**orm **K**ompatibility **C**omposition. It forces all text into a single, standardized representation.

Here is why it is strictly required for your Bengali corpus:

**A. Combining Characters vs. Precomposed Characters**
In Bengali, a word like "কি" (ki) can exist in the text in two ways:

1. **Precomposed:** As a single Unicode character for "কি".
2. **Combining:** As the consonant "ক" (ka) followed by the vowel modifier "ি" (i).
To a human, they look identical. To a computer, they are completely different strings. NFKC forces both variations into the composed form.

**B. The "Khondota" (ৎ) Problem**
The character 'ৎ' (Khanda Ta) is often historically encoded as a standard 'ত' (Ta) followed by a Halant/Virama (্). Modern systems use the dedicated 'ৎ' character. If your OCR outputs one form and the user searches with the other, retrieval fails. NFKC standardizes this.

**C. Complex Ligatures (যুক্তবর্ণ)**
Bengali is heavily reliant on ligatures (e.g., জ্ঞ = জ + ঞ). Different keyboards and OCR engines construct these ligatures differently in Unicode space. NFKC ensures that no matter how the OCR engine constructed the word "বিজ্ঞান" (Science), it will match the user's query perfectly.

**Implementation Note:**
You must apply NFKC normalization to **both** the ingested OCR text before it enters the database, **and** the user's query before it is sent to the embedding model.

def _run_qwen_generate(pil_image: Image.Image, prompt: str, model, processor) -> str:
    # 1. SAFETY VALVE: Cap max pixels to prevent VRAM explosion
    # 1.2 Megapixels is safe for a 16GB T4 while maintaining high readability
    max_pixels = 1200 * 1200 
    w, h = pil_image.size
    if w * h > max_pixels:
        scale = (max_pixels / (w * h)) ** 0.5
        new_w, new_h = int(w * scale), int(h * scale)
        pil_image = pil_image.resize((new_w, new_h), Image.Resampling.LANCZOS)

    messages = [
        {
            "role": "user",
            "content": [
                {"type": "image", "image": pil_image},
                {"type": "text", "text": prompt},
            ],
        }
    ]
    text_prompt = processor.apply_chat_template(
        messages, tokenize=False, add_generation_prompt=True
    )
    inputs = processor(
        text=[text_prompt], images=[pil_image], padding=True, return_tensors="pt"
    )
    inputs = {k: v.to(model.device) for k, v in inputs.items()}

    with torch.no_grad():
        generated_ids = model.generate(
            **inputs,
            max_new_tokens=MAX_QWEN_NEW_TOKENS,
            do_sample=False,
            temperature=None,
            top_p=None,
            top_k=None,
        )
        
    trimmed = [
        out[len(inp):] for inp, out in zip(inputs["input_ids"], generated_ids)
    ]
    output_text = processor.batch_decode(
        trimmed, skip_special_tokens=True, clean_up_tokenization_spaces=False
    )

    # 2. AGGRESSIVE CLEANUP: Free the massive generation activations immediately
    del inputs, generated_ids, trimmed
    if torch.cuda.is_available():
        torch.cuda.empty_cache()

    return output_text[0].strip()

```

### Why this fixes it:

1. **Dynamic Resizing:** If an extremely tall table or wide map sneaks through, the PIL resize logic shrinks it proportionally so it never exceeds ~1.44 million pixels, guaranteeing the visual tokens stay well within the T4's limits.
2. **Immediate Garbage Collection:** `torch.cuda.empty_cache()` at the end of the function ensures the 4-8 GB of activation memory used *during* generation is instantly returned to the GPU, so the next EasyOCR or Qwen call starts with a clean slate.

## Core Components Deep-Dive

### 1. Data Ingestion & Orchestration

* **Driver:** The script reads books sequentially and writes pages to disk one at a time. This prevents RAM bloat, meaning processing a 500-page book takes the exact same amount of memory as a 5-page book.
* **Native Text Recovery:** Before doing any OCR, PyMuPDF checks if the publisher included an actual text layer. If it finds one, it skips the heavy prose OCR entirely, saving massive amounts of compute time.

### 2. Computer Vision Layout Analysis (OpenCV)

Instead of loading an AI model to detect page layouts (which would consume precious VRAM), the pipeline uses classical computer vision.

* It renders the page into a grid of pixels.
* It uses **Morphological Transformations** (`cv2.morphologyEx`) to stretch horizontal and vertical dark pixels. Where these stretched lines intersect, the algorithm identifies a grid (a table or calculation block) and draws a bounding box around it.

### 3. The Hybrid Inference Engine

This is where the pipeline optimizes for the Kaggle T4 GPU:

* **EasyOCR (The Grunt):** Sits in VRAM taking up only ~400MB. It runs over standard paragraphs rapidly.
* **The Quality Gate:** If EasyOCR returns text with a confidence below 70%, or if >15% of the output consists of garbled symbols (which EasyOCR sometimes does on mixed English/Bangla text), the pipeline traps the error.
* **Qwen2.5-VL-3B (The Specialist):** Loaded in `float16`, this model takes up about 6GB of VRAM. It acts as an escalation path. It is only called for highly complex structures (Maps, Tables) or when EasyOCR fails the Quality Gate.

### 4. Memory Management (T4 Safeguards)

Because VLMs allocate massive blocks of memory dynamically based on how many pixels you feed them, the pipeline features two critical fail-safes:

* **The 1.2 Megapixel Cap:** Using standard Lanczos resampling, any image that would crash the GPU is proportionally shrunk before the model sees it.
* **Aggressive Garbage Collection:** `torch.cuda.empty_cache()` is called explicitly after Qwen generates text, instantly destroying the heavy activation tensors so they don't fragment the GPU's memory pool.

from pathlib import Path
from langchain.text_splitter import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain_community.vectorstores import FAISS

# ==============================================================================
# CONFIGURATION
# ==============================================================================
MD_DIR = Path("/kaggle/working/")
INDEX_DIR = Path("/kaggle/working/bangla_books_faiss_index")

# Using a multilingual model that performs excellently on Bengali
EMBEDDING_MODEL = "sentence-transformers/paraphrase-multilingual-mpnet-base-v2"

def main():
    md_files = list(MD_DIR.glob("*.md"))
    if not md_files:
        print(f"No Markdown files found in {MD_DIR}")
        return

    print(f"Found {len(md_files)} Markdown files. Starting ingestion...")

    # 1. Define Markdown hierarchy based on our ocr_helper.py output
    headers_to_split_on = [
        ("#", "Book_Title"),
        ("##", "Page_Number"),
        ("###", "Section_Type"),
    ]
    markdown_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers_to_split_on)

    # 2. Fallback splitter for very long text blocks (e.g., a massive 3-page chapter)
    text_splitter = RecursiveCharacterTextSplitter(
        chunk_size=768, 
        chunk_overlap=100,
        separators=["\n\n", "\n", "।", " ", ""] # Bangla sentence ending (Dari) included
    )

    all_chunks = []

    # 3. Read and Chunk
    for file_path in md_files:
        print(f"Chunking: {file_path.name}")
        with open(file_path, "r", encoding="utf-8") as f:
            md_text = f.read()
        
        # Split by markdown headers
        md_header_splits = markdown_splitter.split_text(md_text)
        
        # Further split long paragraphs
        splits = text_splitter.split_documents(md_header_splits)
        
        # Inject the source file name into metadata
        for split in splits:
            split.metadata["Source_File"] = file_path.name
            
        all_chunks.extend(splits)

    print(f"Total chunks created: {len(all_chunks)}")

    # 4. Embed and Store
    print(f"Loading embedding model: {EMBEDDING_MODEL}...")
    embeddings = HuggingFaceEmbeddings(
        model_name=EMBEDDING_MODEL,
        model_kwargs={'device': 'cuda'} # Will use GPU if available
    )

    print("Generating embeddings and building FAISS index (this may take a moment)...")
    vectorstore = FAISS.from_documents(all_chunks, embeddings)
    
    # 5. Save to disk
    vectorstore.save_local(str(INDEX_DIR))
    print(f"FAISS index successfully saved to: {INDEX_DIR}")

if __name__ == "__main__":
    main()

```

[AI] :Yes, absolutely. Switching to **`BAAI/bge-m3`** is a massive upgrade for this specific pipeline.

While `paraphrase-multilingual-mpnet-base-v2` is a reliable older workhorse, `bge-m3` is currently state-of-the-art for multilingual retrieval.

### Why BGE-M3 Wins Here

* **Native Bangla Prowess:** The "M3" stands for Multi-linguality (trained on over 100 languages). It consistently dominates the MTEB (Massive Text Embedding Benchmark) for non-English languages, meaning it will understand Bengali conjuncts, vocabulary, and semantic nuances much better than older models.
* **Massive Context Window:** Older models like `mpnet` truncate text after 512 tokens. `bge-m3` supports an **8,192 token context window**. This means if your Markdown chunking occasionally produces a very long table or uninterrupted text block, it won't get arbitrarily cut off during embedding.
* **Late-Interaction Synergy:** `bge-m3` supports multi-vector (ColBERT-style) retrieval. For advanced document processing architectures utilizing Vision-Language Models like ColPali, `bge-m3` serves as the perfect text-side counterpart. Both utilize late-interaction paradigms to preserve granular, token-level matching that standard single-vector embeddings often lose.

[AI] :To display similarity scores, you need to call `vectorstore.similarity_search_with_score()` directly instead of using `retriever.invoke()`.

The default LangChain `retriever` interface strips out the score metrics, whereas `similarity_search_with_score()` returns tuples of `(doc, score)`.

Here is your updated retrieval cell:

```python
# ---------------------------------------------------------
# Define your Bengali search query here
# Example: "পাহাড়ি অঞ্চলের ভৌগোলিক বৈশিষ্ট্য" (Geographical features of hilly regions)
# Example: "বাংলাদেশের মানচিত্রে কোন কোন জেলা আছে?" (Which districts are on the map of BD?)
# ---------------------------------------------------------
query = "বাংলাদেশের ভৌগোলিক অবস্থান ও সীমানা" 

print(f"Query: {query}\n" + "="*50 + "\n")

# Perform similarity search with score
# Returns a list of (Document, score) tuples
results = vectorstore.similarity_search_with_score(query, k=3)

for i, (doc, score) in enumerate(results):
    # Retrieve metadata extracted by our MarkdownHeaderTextSplitter
    source = doc.metadata.get("Source_File", "Unknown")
    page = doc.metadata.get("Page_Number", "Unknown Page")
    section = doc.metadata.get("Section_Type", "Body Text")
    
    print(f"Result {i+1}:")
    # Displaying metadata along with the distance score (formatted to 4 decimal places)
    print(f"📍 Source: {source} | Page: {page} | Type: {section} | Distance Score: {score:.4f}")
    print("-" * 50)
    
    # Wrap text for readable notebook output
    wrapped_text = textwrap.fill(doc.page_content, width=80)
    print(wrapped_text)
    print("\n" + "="*50 + "\n")

```

### Understanding the Score in FAISS:

Since `normalize_embeddings=True` was set during indexing:

* FAISS reports **L2 Distance**.
* **Lower is better** (a score closer to `0.0` represents higher semantic similarity / closer match).
* If you prefer a normalized **Similarity Score (0.0 to 1.0, where higher is better)**, you can replace `similarity_search_with_score` with `vectorstore.similarity_search_with_relevance_scores(query, k=3)`.
